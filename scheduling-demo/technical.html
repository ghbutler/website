TECHNICAL APPENDIX · SYNTHETIC ONLY

Data handling and pilot readiness

Data flow

Approved source → restricted validation and aggregation job → current aggregate snapshot → server authorization → TA browser. Prefer aggregation within Cornell’s approved environment. The public demo instead generates synthetic schedules locally and is not connected to Cornell.

Public GitHub Pages version

This package is a static, browser-only demonstration. It loads bundled public course snapshots and catalog rules, then generates 120 mock students using a fixed integer seed (20261106, Mulberry32 PRNG). It computes aggregates locally. There is no API, server-side authorization, login, live feed, telemetry, or expiration. Public source code and synthetic schedules can be inspected; this is intentional and unsuitable for real records.

Generation and constraints

First-year fall courses: 5009, 5111, 5120, 5210 and 5310, including required discussions. Second-years receive accounting, two distinct approved concentration electives, two distinct remaining requirement-role courses, and capstone I. Their prior fall/spring schedules establish gateway and selected prerequisites. Each year represents all seven concentrations. Section choices reject overlapping meetings. Inclusive course date ranges determine conflicts for the November 2–6 reference week.

The model does not certify degree completion. Required 2025–26 PUBPOL 5121 is absent from the saved term listings; no substitution is invented. Catalog transitions and assumed internships require institutional confirmation. JavaScript’s seeded generator preserves the constraints, not Python’s exact random sequence, so section counts may differ from the earlier prototype.

Separate backend prototype

The retained backend prototype tests mock section authorization, atomic validated batch replacement, source timestamps and stale-data handling. It is not included or deployed by this static package. Its operational design would send only permitted aggregates to an authenticated browser and use a Cornell-approved data pipeline. Those capabilities remain separate from this public demonstration.

Security review before real records

Replace the demo identity with validated Cornell SSO sessions; fail closed when assignment authority is unavailable or stale. Implement prompt revocation, session expiry, secret management, restricted service accounts, encrypted transport/storage, rate limits and safe operational logging. Verify cross-section and future cross-department isolation, caching behavior, source authenticity and replay handling. Test authorization using the final deployment stack. Assign an incident contact and kill switch; agree on minimal retention and backup expiry. Suppress raw records in error monitoring, analytics, AI tools, and support tickets.

Residual risks include inference from small/overlapping groups and successive updates, screenshots by authorized users, compromised accounts, incomplete calendars, and misuse as attendance evidence. Access controls and boolean output do not eliminate these risks.
